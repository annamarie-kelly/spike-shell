01Not a coding tool

Built for all your work.

Zed, Cursor, and VS Code are coding tools. Spike is where everything happens: essays, specs, research, design, data, landing pages, this page included.

The interface to all of it is the same: an agent, a file, a preview, fast iteration. The code IDEs are aimed at code; Spike is aimed at the work, whatever it happens to be.

02Terminals

Every tab is a session. Groups are durable workspaces.

When the agent writes the output, the thing you manage isn't files, it's contexts. So a tab isn't a document, it's a live session, and groups of sessions are the workspaces you keep coming back to.

Each tab is its own agent session, Claude Code or OpenAI Codex, with a real PTY underneath. Add with +, rename anytime, close with ×. Then organize them the way a browser organizes tabs:

  • Chrome-style tab groups. Group sessions, name them, give each a color, collapse and expand.
  • Context that travels. Each group carries its own context prompt, injected into every session that spawns inside it. A "reviews" group can know your review checklist; a project group knows its conventions.
  • Any folder. Pick a folder with the native dialog, and the tree re-roots and new terminals spawn there. Spike is not tied to any one project.

03Preview

A preview that edits.

The loop is see → react → refine → reproduce, and the preview is where it closes. It isn't a coding convenience, it's the feedback surface. The question stops being "is this line correct" and becomes "did the thing get built, and does it look right."

Reading code, you can judge a lot from the source. Reading the agent's output, you have to look at the result, so the preview here is load-bearing, not an afterthought.

Markdown renders with clickable wikilinks. HTML, CSV, JSON, images, PDF, and media all display in place. And behind every text file sits a syntax-highlighted editor with ⌘S save, and the preview pane is also where you fix the thing you're looking at.

Screenshots flow the other way: drag an image onto a terminal, even the floating thumbnail right after ⌘⇧4, and it lands in the prompt as the agent's own image attachment. Other files drop their path, same as dragging from the tree.

04The log

Spike records. You ask the questions.

An append-only action log lives at ~/.spike/logs/<day>.jsonl, one JSON event per line, server-stamped: tab_spawn, file_open, group_assign, file_save, spike_open. It even records file_change for edits that happen outside Spike's own UI, by promoting what the file watcher already sees.

Most tools want to be smart at you. Spike does none of that on purpose: the log is a record, and the questions are yours. Open a session and say "read my spike log and tell me how to tighten my workflow", write a retro, audit your own habits. The intelligence layer is your agent plus your curiosity, not a suggestion engine baked into the tool.

05The bridge

Two commands connect the agent to the glass.

The agent is a terminal program Spike doesn't own, Claude Code or OpenAI Codex, your pick. The bridge is how it and the UI stay in sync anyway: two small commands on the embedded terminal's PATH, one pushing, one pulling.

agent → ui
spike open <path>

Opens a file into the preview (or re-roots the tree) instead of summarizing it back at you in prose.

⟶⟵
ui → agent
spike context

Reports what you're looking at, open file, tree selection, project root, so "this file" resolves to a real path without asking.

The page reports its focus to a tiny localhost listener on every change, and spike context reads it back, paths only, never contents, so the agent opens the file itself when it needs the bytes. An editor with a built-in assistant can wire this up internally; the seam here is open, so it works for an agent you brought yourself.

06Tiling

Grab a pane. Drop it on an edge. The layout is yours.

Seeing the work means putting the pieces side by side, the session, the file, the result, and arranging them by hand. The layout engine underneath is a plain recursive split tree, unit-tested and framework-free. What that buys you in practice:

Drag to split

Grab a pane by its header, drop it on another pane's edge to split, or its center to stack.

Tear off a tab

Drag a terminal tab off the strip and that session gets its own pane.

Files dock too

Drag a file from the tree onto an edge and the preview opens right there.

State survives

The renderer re-parents live DOM nodes, so xterm scrollback and editor state survive any drag. The layout persists across launches.

07Under the hood

Deliberately small.

  • Backend: Rust. A real PTY per terminal via portable-pty, filesystem ops, a file watcher, and a tiny localhost listener for the CLI bridge.
  • Frontend: plain DOM. xterm.js for the terminals, no UI framework for everything else. One shim (ipc.ts) is the only file that knows Tauri exists.
  • Builds in milliseconds. esbuild bundles the frontend; type-checking is a separate, advisory gate that never blocks a build.
  • Layout: a recursive split tree. Unit-tested, framework-free, persists across launches.

08Run it

Download, drag, launch.

Grab the signed .dmg, drag Spike to Applications, open it. It's notarized by Apple, so no Gatekeeper warning and no toolchain to install. You'll need Claude Code or OpenAI Codex on your PATH to use it. (Spike auto-detects both, pick the default in Settings, or per-tab from the + launcher.)

Download for Mac Apple silicon

Build from source

Prefer to build it yourself? Requires Node 18+ and the Rust toolchain.

❯ git clone https://github.com/annamarie-kelly/spike.git
❯ cd spike
❯ npm install
❯ npm run dev:tauri    # build + launch the app

To install it as a real app, builds a release bundle and copies it to /Applications:

❯ npm run install:app
